# AGENT.md — InvertoryHUD
## Разработка DLL-модификации интерфейса The Settlers II — Юбилейное издание

**Версия проекта:** 0.1  
**Тип проекта:** Native DLL Mod / In-Game HUD Extension  
**Язык:** C++  
**Графический API:** DirectX 9  
**Целевая игра:** The Settlers II — Юбилейное издание. Игра лежит в корне s2. С ней и работаемю
**Основная задача:** Добавление постоянно видимой панели глобальных ресурсов непосредственно в игровой интерфейс.
**ОРабочая папка:** \s2\s2_invertory. Тут пишем весь код, относящиеся к задумке. Остальные папки можно смотреть, как там реализовано инжектирование DLL. В \s2\Work\Game\bin есть LuaDebugger.dll, он инжектирует в UI SADK кнопку новой кампании. Может пригодится.

# 1. ЦЕЛЬ ПРОЕКТА

Разработать независимую DLL-библиотеку `InvertoryHUD.dll`, которая интегрируется в процесс оригинальной игры The Settlers II — Юбилейное издание.

DLL должна расширять оригинальный интерфейс игры, добавляя компактную однострочную панель глобальных ресурсов игрока.

Модификация не должна требовать изменения исходного EXE игры.

Главная задача — исследовать внутреннее устройство оригинального игрового движка, определить способы получения данных инвентаря и внедрения собственной графики в существующий DirectX 9 Rendering Pipeline.

**Принципиальное требование:** использовать оригинальные игровые данные. Не создавать собственную экономическую модель и не пытаться вычислять запасы ресурсов самостоятельно.

В игре уже существует экран:

`Статистика → Инвентарь (Все товары в ратуше и на складах)`

Он отображает глобальные запасы товаров игрока.

Необходимо выяснить, откуда этот экран получает информацию, и использовать тот же источник данных для собственной HUD-панели.

Перед началом работы изучить структуру имеющегося проекта.

- Оригинальные игровые ресурсы.
- Оригинальные DLL-библиотеки.

Доступные оригинальные библиотеки:

- matchmaking.dll
- binkw32.dll
- expat.dll
- fmod.dll
- tincat3.dll

Предполагается, что игра использует DirectX 9.

Это необходимо подтвердить исследованием оригинального исполняемого файла.

## 2.1. Правила исследования

1. Не изменять оригинальный EXE без отдельного обоснования.
2. Не изменять оригинальные игровые DLL.
3. Не переписывать игровые подсистемы.
4. Не создавать дублирующие структуры экономики.
5. Использовать существующие функции и структуры игры, если это технически возможно.
6. Не придумывать адреса, сигнатуры, смещения и названия функций.
7. Все найденные адреса и структуры должны иметь подтверждение.
8. Не использовать OCR и распознавание изображения для получения ресурсов.
9. Не использовать чтение изображения экрана вместо чтения игровых данных.
10. Не использовать внешнее окно поверх игры как основное решение.

Декомпилированный код является основным источником для исследования, но окончательные выводы необходимо сверять с оригинальным бинарным файлом.

```text
The Settlers II.exe

       +-------------------------+
                 |

       +---------+----------+
       |         |          |

       |                    |
```

Это предварительная архитектура. Агент должен проверить её техническую реализуемость и при необходимости предложить более эффективную.

## 3.1. Основные компоненты

### GameBridge

Отвечает за взаимодействие с игровым процессом:

- обнаружение игрового контекста;
- определение текущего игрока;
- получение необходимых указателей на игровые структуры;
- проверку валидности указателей;
- определение состояния игры;
- безопасное завершение работы при выходе из игры.

### InventoryReader

Отвечает за получение данных глобального инвентаря.

### ResourceTracker

Отвечает за отслеживание изменений ресурсов, поступления и расходования.

### HUDRenderer

Отвечает за графическую отрисовку панели.

### SettingsWindow

Отвечает за окно настройки отображаемых ресурсов.

### HUDConfig

Отвечает за чтение и сохранение настроек.

# 4. ЭТАП P1 — ИССЛЕДОВАНИЕ ИГРОВОГО ИНВЕНТАРЯ

Это один из наиболее важных этапов.

До написания InventoryReader необходимо полностью исследовать существующую систему статистики игры.

## 4.1. Найти экран «Статистика → Инвентарь (Все товары в ратуше и на складах)»

В декомпилированном коде необходимо исследовать:

- создание окна статистики;
- обработчики переключения вкладок;
- функцию отображения инвентаря;
- функцию заполнения таблицы ресурсов;
- получение значений товаров;
- обработку смены игрока;
- обновление статистики;
- перечисления типов ресурсов.

Поиск начинать с идентификаторов строк, названий элементов интерфейса, названий ресурсов и функций, связанных со статистикой.

Не ограничиваться поиском по строке `Inventory`.

Использовать связанные сущности:

- Ware
- WareType
- Goods
- GoodType
- Player
- PlayerManager
- Inventory
- Statistics
- WareStatistics
- Resource
- ResourceManager
- Stock
- Amount
- Count
- Supply
- Consumption
- Production

Это ориентировочные поисковые термины, а не утверждение о названиях реальных классов.

## 4.2. Найти источник глобального инвентаря

Необходимо установить:

1. Где хранится информация о запасах игрока.
2. Как устроена структура игрока.
3. Где находится информация о товарах.
4. Как представлены типы товаров.
5. Как определяется текущий игрок.
6. Как суммируются запасы.
7. Включаются ли в статистику товары, находящиеся на складах, в производстве и в транспортировке.
8. Какие товары не учитываются.
9. Как обновляются значения инвентаря.

Особое внимание уделить различию между:

- запасом на конкретном складе;
- запасом конкретного типа товара;
- глобальным запасом игрока;
- количеством товаров в производстве;
- количеством товаров в транспортировке.

Нас интересует именно тот показатель, который выводится в оригинальном окне «Статистика → Инвентарь».

## 4.3. Исследовать функцию получения количества ресурса

Необходимо определить, существует ли готовая функция, возвращающая количество конкретного товара.

Например, условная функция:

```cpp
int GetPlayerWareAmount(
    int playerId,
    WareType ware
);
```

Это только пример предполагаемого интерфейса.

Если готовой функции нет, исследовать внутренние структуры и алгоритм подсчёта.

Предпочтительный вариант — использовать уже существующую функцию игрового движка.

Не дублировать алгоритм, если есть возможность вызвать оригинальную реализацию.

## 4.4. Исследовать обновление данных

Установить:

- пересчитывается ли инвентарь каждый игровой тик;
- обновляется ли статистика по событиям;
- есть ли кэш;
- зависит ли обновление от открытия окна статистики;
- можно ли безопасно получить данные без открытия оригинального окна.

Последний пункт особенно важен.

HUD должен обновляться даже тогда, когда пользователь вообще не открывает экран статистики.

## 4.5. Результат P1

Создать документ:

`docs/INVENTORY_RESEARCH.md`

В нём обязательно указать:

- найденные структуры;
- найденные функции;
- адреса функций в оригинальном EXE;
- сигнатуры;
- аргументы;
- возвращаемые значения;
- смещения полей структур;
- типы данных;
- взаимосвязи объектов;
- алгоритм подсчёта глобального инвентаря;
- подтверждение соответствия оригинальному окну статистики.

Для каждой функции указать уровень достоверности:

- VERIFIED — подтверждена отладкой или непосредственным исследованием бинарного файла.
- HIGH — подтверждена декомпиляцией и анализом вызывающего кода.
- MEDIUM — обоснованная гипотеза.
- LOW — неподтверждённое предположение.

Не использовать MEDIUM и LOW в критических операциях DLL без дополнительной проверки.

**P1 нельзя считать завершённым, пока не найден достоверный источник глобального инвентаря.**

# 5. ЭТАП P2 — ИССЛЕДОВАНИЕ DIRECTX И ИНТЕГРАЦИИ HUD

Необходимо исследовать графическую подсистему оригинальной игры.

Цель — встроить собственную графическую панель непосредственно в игровой Rendering Pipeline.

## 5.1. Подтвердить используемый API

Исследовать:

- создание Direct3D9;
- создание Direct3DDevice9;
- параметры устройства;
- полноэкранный и оконный режимы;
- основной цикл отрисовки;
- механизм Present;
- обработку потери устройства;
- восстановление устройства.

Найти фактические точки входа графической подсистемы.

## 5.2. Исследовать оригинальный UI Rendering

Найти механизм, через который игра отрисовывает:

- окна;
- кнопки;
- иконки;
- текст;
- DDS-подложки;
- всплывающие элементы;
- курсор;
- панели статистики.

Определить:

- координатную систему;
- масштабирование интерфейса;
- разрешение игрового viewport;
- порядок отрисовки UI;
- порядок отрисовки игрового мира;
- способ загрузки текстур;
- способ вывода текста.

Особое внимание уделить возможности использования оригинальных игровых текстур и шрифтов.

Не требуется создавать окна средствами оригинального UI, если это слишком сложно или система не предусматривает динамическое создание окон.

Предпочтительная реализация — собственная отрисовка через DirectX 9.

## 5.3. Исследовать способы внедрения

Рассмотреть следующие варианты:

1. Перехват IDirect3DDevice9::Present.
2. Перехват IDirect3DDevice9::EndScene.
3. Перехват оригинальной функции отрисовки UI.
4. Встраивание в существующий игровой Rendering Pipeline через найденную точку расширения.

Для каждого способа оценить:

- сложность;
- стабильность;
- совместимость;
- возможность корректного отображения поверх оригинального UI;
- влияние на производительность;
- обработку Reset и потери устройства.

Выбрать один основной вариант и один резервный.

Не устанавливать несколько конфликтующих хуков без необходимости.

## 5.4. Требования к отрисовке

HUD должен:

- отображаться поверх игрового мира;
- корректно работать в оконном и полноэкранном режимах, если поддерживаются игрой;
- не мешать оригинальному интерфейсу;
- учитывать разрешение экрана;
- не перехватывать клики, если пользователь нажимает за пределами элементов HUD;
- корректно работать при смене разрешения;
- восстанавливаться после потери DirectX Device.

## 5.5. Работа с оригинальными ресурсами

Исследовать доступные игровые DDS-ресурсы.

По возможности использовать оригинальные иконки товаров.

Если подходящих иконок нет, предусмотреть собственный набор небольших изображений.

Не создавать тяжёлые графические ресурсы.

Все текстуры загружать один раз и хранить в кэше.

# 6. ЭТАП P3 — СИСТЕМА ПОЛУЧЕНИЯ РЕСУРСОВ

Реализовать компонент:

`InventoryReader`

## 6.1. Требования

InventoryReader должен:

- определять текущего игрока;
- получать глобальный инвентарь;
- получать значения всех типов товаров;
- возвращать данные в унифицированной структуре;
- корректно обрабатывать отсутствие игрового контекста;
- обнаруживать смену игрока;
- не обращаться к недействительным указателям;
- не вмешиваться в игровые данные.

Пример внутренней структуры:

```cpp
struct ResourceData
{
    int wareId;
    int amount;

    int previousAmount;

    int income;
    int consumption;

    int netChange;
};

struct InventorySnapshot
{
    int playerId;
    uint64_t gameTick;

    std::vector<ResourceData> resources;
};
```

Структура предварительная. Адаптировать её к реальным типам оригинальной игры.

## 6.2. Обновление

Не нужно получать данные каждый кадр.

Предлагаемый начальный интервал:

500–1000 мс.

Однако агент должен проверить:

- можно ли безопасно обращаться к игровым структурам из отдельного потока;
- требуется ли чтение исключительно из игрового потока;
- есть ли готовые события обновления.

Предпочтительно выполнять чтение в безопасной точке игрового цикла.

Если используется отдельный поток, он не должен самостоятельно обращаться к игровым объектам без подтверждения потокобезопасности.

Передача снимков данных в HUD должна осуществляться через потокобезопасный механизм.

# 7. ЭТАП P4 — ДОХОД И ПОТРЕБЛЕНИЕ

Это дополнительная, но желательная возможность.

Необходимо исследовать экономическую систему игры.

Найти функции и события:

- поступления товаров;
- производства;
- потребления;
- перемещения товаров;
- продажи или обмена;
- потери товаров;
- уничтожения складов;
- изменения запасов.

## 7.1. Приоритет №1 — оригинальные счётчики

Проверить, существуют ли в оригинальном движке готовые значения:

- Production;
- Consumption;
- Income;
- Expenses;
- WareStatistics.

Если существуют, исследовать их назначение и использовать оригинальные данные.

## 7.2. Приоритет №2 — отслеживание операций

Если готовых счётчиков нет, исследовать места изменения глобального инвентаря.

Возможна реализация собственного наблюдателя:

```cpp
struct ResourceFlow
{
    int produced;
    int consumed;
    int imported;
    int exported;
};
```

Необходимо отличать:

- производство;
- потребление;
- перемещение между складами;
- транспортировку;
- торговлю.

Перемещение товара внутри одного поселения не должно автоматически считаться производством или потреблением.

## 7.3. Резервный вариант

Если достоверно разделить производство и потребление невозможно, использовать чистое изменение инвентаря:

```cpp
netChange = currentAmount - previousAmount;
```

В интерфейсе обязательно обозначить это как изменение запаса, а не доход.

Не показывать выдуманные показатели.

# 8. ЭТАП P5 — СОЗДАНИЕ HUD

Основной интерфейс должен быть максимально компактным.

## 8.1. Внешний вид

Одна горизонтальная строка:

```text
┌──────────────────────────────────────────────────────────────┐
│ 🌲 125 +4 │ 🪨 86 +2 │ 🌾 215 -3 │ 🍞 48 -5 │ ⚒ 31 +1 │ ⚙ │
└──────────────────────────────────────────────────────────────┘
```

Каждый ресурс представляет собой:

- иконку;
- количество;
- необязательное значение изменения.

Не использовать большие карточки, графики, таблицы и тяжёлые декоративные элементы. Брать икноки ресурсов прямо из движка и подписи ресурсов при наведении мышки тоже из движка. Важно при смене локализации.

Стиль:

- плоский;
- минималистичный;
- компактный;
- читаемый;
- визуально подходящий для RTS.

Допускается, что панель будет немного отличаться от оригинального оформления игры.

## 8.2. Состав панели

Каждый элемент:

```text
[RESOURCE_ICON] [AMOUNT] [CHANGE]
```

Пример:

```text
🌲 125 +4
```

Цветовая индикация:

- зелёный — положительное изменение;
- красный — отрицательное изменение;
- нейтральный — отсутствие изменений.

Предусмотреть возможность отключения отображения изменений.

## 8.3. Положение

Предусмотреть настройку:

- верхняя часть экрана;
- нижняя часть экрана;
- горизонтальное смещение;
- вертикальное смещение.

По умолчанию панель располагается в верхней части экрана.

Не допускать перекрытия важных элементов оригинального интерфейса без возможности перемещения панели.

## 8.4. Масштабирование

Предусмотреть:

- размер иконок;
- высоту панели;
- размер текста;
- промежутки между ресурсами.

Необходимо корректно работать с разными разрешениями экрана.

# 9. ЭТАП P6 — ОКНО НАСТРОЕК

В правой части HUD разместить кнопку с иконкой шестерёнки.

Нажатие открывает отдельную небольшую панель настроек.

## 9.1. Настройки ресурсов

В окне отображается полный список типов товаров, обнаруженных в оригинальном движке.

Для каждого товара:


# 12. ТЕХНИЧЕСКИЕ ТРЕБОВАНИЯ

## 12.1. Язык и компиляция

Использовать C++.

Стандарт C++17 или более новый, если совместимость с целевой средой позволяет.

Система сборки — CMake.

Компилятор — MSVC.

Обязательно определить архитектуру оригинальной игры.

Если игра 32-битная, DLL также должна быть 32-битной.

Не предполагать архитектуру без проверки.

## 12.2. Зависимости

Использовать минимальное количество внешних библиотек.

Приоритет:

- WinAPI;
- DirectX 9 SDK;
- стандартная библиотека C++;
- MinHook или аналогичная лёгкая библиотека для хуков, если потребуется;
- собственная простая система INI.

Не использовать тяжёлые UI-фреймворки.

Не использовать Qt.

Не использовать Electron.

Не использовать отдельный Chromium UI.

Не внедрять ImGui в финальную версию HUD без отдельного обоснования. Он может применяться для диагностического прототипа, но итоговая панель должна быть максимально лёгкой.

## 12.3. Производительность

HUD не должен заметно влиять на FPS.

Требования:

- отсутствие выделения памяти каждый кадр;
- кэширование текстур;
- отсутствие повторной загрузки ресурсов;
- отсутствие тяжёлых вычислений в Render Hook;
- минимальная частота опроса инвентаря;
- отсутствие блокирующих операций;
- отсутствие постоянного логирования в релизной сборке.
